# Horoshop Sales Report

Отчёт продаж + ABC-анализ магазина на Хорошопе через API.

## Когда применять

- Запросы про продажи / выручку / средний чек / заказы магазина на Хорошопе
- «Что продаётся, что нет?», «Где деньги делаются?»
- ABC-анализ, Парето, топ-товары
- Анализ заказов по периодам, UTM-источникам

## Принципы

1. **«Доставлен» = деньги.** Выручка считается **только по заказам со статусом 3 (доставлен)**. Все остальные — потенциальные деньги, отдельная статистика.
2. **Прозрачно про статусы.** Если у клиента кастомные статусы заказов — скилл упомянет где их посмотреть (`orders/get_available_statuses`).
3. **AOV без доставки.** `total_sum` = товары + скидки, **без** `delivery_price`. Это чистая выручка по товарам.
4. **ABC по выручке доставленных** — стандарт. Парето 80/15/5.

## Pipeline

```
[1] Вводные: домен + креды (если auth не прошёл — инструкция создать API-юзера)
        ↓
[2] Период: --from / --to (по умолчанию последние 30 дней)
        ↓
[3] Выгрузка orders/get с пагинацией (limit=500, offset)
        ↓
[4] Расчёты: сводка / динамика / ABC / UTM / payment_type
        ↓
[5] SALES_REPORT.md
```

## Шаг 1 — Вводные

Спроси (если не указано):
1. **Домен** магазина
2. **Логин и пароль** API-пользователя (если нет — инструкция как в `horoshop-full-audit`: создать `api` с ролью Owner)
3. **Период:** за какой период анализ? По умолчанию последние 30 дней. Можно «за последние 90 дней», «за апрель», «с 2026-01-01 по 2026-03-31».

## Шаг 2 — Auth check

```bash
curl -s -X POST https://<DOMAIN>/api/auth/ \
  -H "Content-Type: application/json" \
  -d '{"login":"<LOGIN>","password":"<PASSWORD>"}'
```

Если фейл — выдай инструкцию по созданию API-юзера (та же что в `horoshop-full-audit/references/api_admin_setup.md`).

## Шаг 3 — Запуск отчёта

```bash
mkdir -p sales_<domain>
cd sales_<domain>
HOROSHOP_DOMAIN=<DOMAIN> HOROSHOP_LOGIN=<LOGIN> HOROSHOP_PASSWORD=<PASSWORD> \
  python3 ${SKILL_DIR}/scripts/sales_report.py \
  --from 2026-04-01 --to 2026-04-30
```

Скрипт:
- Авторизуется
- Выгружает все заказы за период (с пагинацией)
- Считает: сводку, динамику по дням, по неделям, ABC, UTM, способы оплаты, способы доставки
- Сохраняет `orders.json` (raw) и `SALES_REPORT.md` (отчёт)

Если деп нет:
```bash
python3 -m pip install --user --break-system-packages requests
```

## Шаг 4 — Показ отчёта

Прочитай `SALES_REPORT.md` и покажи **краткую сводку**:
- Период, всего заказов / доставленных
- Общая выручка, средний чек
- Топ-3 товара по выручке
- ABC: сколько товаров в группе A
- Топ UTM-источник

Полный отчёт — ссылка на файл, не вываливай в чат.

## Шаг 5 — Интерпретация (опционально)

Если пользователь просит «что с этим делать» — обратись к `references/interpretation.md`. Там сценарии:
- AOV падает по неделям → почему и что делать
- Группа A слишком узкая (риск концентрации)
- Высокий % отменённых
- UTM source = (none) у >50% заказов → утечка трекинга

## Tone of voice

Лаконично, без воды. Цифры — главное. Графики через Markdown-таблицы. Spike-стиль.

## Reference files

- `references/orders_api.md` — справочник по `orders/get` endpoint (поля, статусы, фильтры)
- `references/interpretation.md` — как читать ABC/Парето, что значат метрики, типичные паттерны

## Что НЕ делать

- ❌ Не считать выручку по всем статусам — только доставленные. Иначе цифра завышена в 1.5-2 раза
- ❌ Не путать `total_default` (без скидок) с `total_sum` (с учётом скидок). Считаем `total_sum`
- ❌ Не суммировать `delivery_price` к выручке товаров — это разные деньги (для агентства часто не учитываются)
- ❌ Не строить графики через сторонние библиотеки (matplotlib и т.п.) — только Markdown-таблицы и текстовые спарклайны
